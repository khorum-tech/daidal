# C4 and drill-down

The [C4 model](https://c4model.com) describes one system at four levels of detail, each a diagram of its own: who uses the system, what it is made of, what one part is made of, and how that part is written. Daidal draws the first three in C4 notation and links the levels, so you can walk from the overview down to the detail and back.

You don't need all four. A Context and a Container diagram are enough for most systems.

## The four levels

| Level | Kind | Shows | A node here is |
|---|---|---|---|
| 1 | **C4 Context** | The system, the people who use it and the other systems it talks to | a person or a whole system |
| 2 | **C4 Container** | What runs inside one system | an app, a service or a data store |
| 3 | **C4 Component** | What one container is made of | a module or component |
| 4 | **C4 Code** | How one component is written | a class, function or table |

Start a level from its template when you make a diagram, or set a diagram's **Kind** in its sheet (press its name in the header). [Types and icons](/app/docs/types-and-icons) says what each kind offers first under **+ Add**, and how C4 cards are drawn. Changing a kind loses nothing.

## Code blocks

At the Code level a node tells more than a name: what the thing holds, what it does, and where it lives. Give a node **members**, **functions** or a **path** and its card becomes a code block.

- **Name**, in monospace: the class, function, file or table.
- **Subtitle**: one line on why it exists.
- **Path**: where it lives, such as `src/lib/parser.ts`. A long path keeps its end, the file's name. A link works too, and opens from the node's details.
- **Members**: what it holds, a line each: a class's fields, a file's exports, a table's columns.
- **Functions**: what it can do, each drawn as a signature under its own rule. Keep to the public surface.
- **Language**: what it is written in. Its functions read as that language writes them; with none, they read in a neutral form any reader follows.

| Written in | `check` reads as |
| --- | --- |
| Any language | `check(batch: Batch) → Verdict` |
| Java, C# | `Verdict check(Batch batch)` |
| Kotlin | `fun check(batch: Batch): Verdict` |
| TypeScript | `check(batch: Batch): Verdict` |
| JavaScript | `check(batch) → Verdict` |
| Python | `def check(batch: Batch) -> Verdict` |
| Ruby | `def check(batch) → Verdict` |
| Go | `func check(batch Batch) Verdict` |
| Rust | `fn check(batch: Batch) -> Verdict` |
| Swift | `func check(batch: Batch) -> Verdict` |

The language changes only how the card writes its functions. Each function keeps the same name, parameters and return type whatever the language, so you can change it, or leave it unset, without losing anything.

A block shows six lines in all, members and functions together; past that, each counts what it leaves out, and the details list them all.

Select a node in a C4 Code diagram to edit these under its notes. Members are typed one a line. **Written in** sets the language. Each function has its own fields, stacked to fit a phone or a tablet: its **name**, its **parameters** (a name and a type each, added with **+ Parameter**), what it **returns**, and a note on what it does. **+ Add function** adds one, and × removes a function or a parameter. If a box already lists functions as text, in its members, subtitle or notes, a button moves them into fields, and leaves the rest of the text where it was.

The block grows to hold its lines, so nothing spills and you don't resize it by hand. Any node in any diagram that has members, functions or a path draws the same way, except a C4 notation card or a sticky note. The functions' notes show in the node's details and when presenting, not on the card.

In the [config format](/app/docs/config), a function is a map, or a signature on one line that reads into the same map:

```yaml
nodes:
  - id: parser
    name: ConfigParser
    type: Class
    subtitle: Reads a config into a document.
    path: packages/core/src/config.ts
    members: ["lang: ConfigLang"]
    language: typescript
    functions:
      - name: readConfig
        params:
          - name: text
            type: string
        returns: ReadConfig
        notes: Checks a config, then reads it.
      - "configText(doc: DaidalDoc): string"
```

Daidal writes functions back as maps, so an exported config always has the same shape. `language` takes `java`, `kotlin`, `typescript`, `javascript`, `python`, `ruby`, `go`, `rust`, `csharp` or `swift`, and reads names such as `C#` or `ts` too.

## Tables

A node of type **Table** with columns draws as a table card, so every table reads the same way: its name, then a row per column with its key, its name and its data type. A key shows as a badge: **PK** for a primary key, **FK** for a foreign key, **UQ** for unique. Past ten columns, the last row counts the rest, and the details list them all.

Select a Table to edit its columns under its notes. Each column has its **name**, its **key** and its **data type**, stacked to fit a phone or a tablet; the usual data types are offered as you type, and any other works too. **+ Add column** adds one, the arrows move it, and × removes it. A Table that lists its columns as members, one `name: type` a line, keeps drawing as before and offers a button to make them columns.

In the [config format](/app/docs/config), a column is a map, or a line that reads into the same map:

```yaml
nodes:
  - id: orders
    name: orders
    type: Table
    subtitle: One row per order.
    columns:
      - "PK id: uuid"
      - name: customer_id
        type: uuid
        key: fk
      - "placed_at: timestamptz"
```

Daidal writes columns back as maps. Each column the editor saves keeps an id that stays the same through renames, ready for drawing relationships between tables later.

## Linking one level to the next

A node can open another diagram in the same workspace: a system opens its containers, a container its components. Select the node, and in its details use **Zoom in**.

- **Link a diagram to zoom into** picks a diagram you already have. The card then shows a magnifying glass.
- **New C4 … diagram** makes the level below and links it in one step. It appears on a node in a C4 diagram that zooms into nothing yet. The new diagram is named after the node, and starts with the node as a container and everything it connects to placed around it.
- **New C4 … diagram above**, under **Zoom out**, goes the other way from any level below Context. The new diagram holds the node and what it connects to, and the node zooms back down to the diagram you started from. The diagram you were in isn't changed.

![A container selected in a C4 Container diagram, its details showing the diagram it zooms into under Zoom in, and New C4 Context diagram above under Zoom out](/app/docs-images/c4-zoom.png)

Undo takes a link back. A diagram made this way stays; delete it from its sheet if you don't want it.

## Moving between levels

- **Down:** double-click a node that zooms in, press ⌘↓ with it selected, or press its button under **Zoom in** (on a phone, the only way). A node that zooms into several diagrams opens its details so you can choose.
- **Up:** press a diagram in the header, or ⌘↑ for the one just above. You arrive with the node that zoomed in selected.

## Knowing where you are

The header keeps your place while you move.

- **The level.** Before a C4 diagram's name sits a badge with its kind, such as **C4 Component**, and four small bars with its level lit. Each diagram on the way up carries the same bars; point at them for the kind. On a phone the badge is the bars alone. A freeform diagram shows none.
- **The way up.** The header lists the diagrams above this one, outermost first. It shows them even when you opened the diagram directly, as long as just one diagram zooms into each level. Where two diagrams zoom into the same one, the list stops there.
- **What's linked.** A badge by the name, such as **↑1 ↓2**, counts the diagrams above and below. Press the name: **Linked diagrams** lists them all, each one press away.

![A C4 Component diagram two levels down, the header showing the Context and Container diagrams above it and a badge naming this one C4 Component](/app/docs-images/c4-levels.png)

A link to a diagram you can't see doesn't show. Links follow a workspace through a backup and import.

## How the levels stay connected

When Daidal makes a level for you, each node it carries over remembers the node it stands for one level up, as a `ref`. That is how the boundary in a Container diagram knows it is the system from the Context diagram.

In the [config format](/app/docs/config) both show plainly. A link down to the next level sits in a node's `links`; the tie up to the level above sits in `ref`, as the upper diagram's id, a `#`, and the node's id there. This is part of a Container diagram (real diagram ids are longer):

```yaml
nodes:
  - id: staff
    name: Finance Staff
    type: actor
    ref: "ledger-context#staff"
  - id: postings
    name: Postings Service
    type: service
    links:
      - diagram: postings-components
boundaries:
  - id: scope
    label: Ledger
    ref: "ledger-context#ledger"
```

Finance Staff is the same person as in the Context diagram, the Ledger boundary is the system from that diagram, and Postings Service zooms into its own Component diagram.

An [AI connected to Daidal](/app/docs/connecting-ai) reads and writes the same fields, so it can build a linked set of diagrams or add a level to one you have.
